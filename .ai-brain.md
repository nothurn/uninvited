## hauntedcore dependency — mandatory, wired via composite build

Same composite-build mechanism as `horrorchatmessages`
(`includeBuild('../hauntedcore')` in `settings.gradle`,
`compileOnly "com.horrortricks.hauntedcore:hauntedcore:1.0.0"` in
`build.gradle`), confirmed working via `:hauntedcore:compileJava` appearing
in the build log. **Different from horrorchatmessages in one important way:**
this dependency is genuinely mandatory, not optional — `mods.toml`
originally declared `mandatory=true`, and the code has zero `ModList` guards
before touching hauntedcore classes. Still used `compileOnly` rather than
`implementation` (hauntedcore ships as its own separate mod jar either way;
Gradle bundling isn't what enforces the mandatory relationship, the
`neoforge.mods.toml` dependency declaration is) — confirmed hauntedcore
classes are **not** bundled into this mod's own jar.

## ★ Metadata fix found while verifying: the MDK template silently dropped the hauntedcore dependency

The standard MDK `neoforge.mods.toml` template only auto-generates
`neoforge`/`minecraft` dependency blocks — it has no notion of a
project-specific extra dependency, so copying it as-is (from Package 3)
meant the built jar's metadata **said nothing about needing hauntedcore at
all**, silently losing the mandatory relationship the original 1.20.1
`mods.toml` declared. Caught this specifically by checking the generated
`neoforge.mods.toml` inside the built jar, not just assuming the template
was complete. Fixed by adding a real
`[[dependencies.phantomjoin]] modId="hauntedcore" type="required" ...`
block to `src/main/templates/META-INF/neoforge.mods.toml`, matching the
original decompiled `mods.toml`'s `mandatory=true`/`ordering="AFTER"`/
`side="CLIENT"` declaration translated to 1.21.1 toml syntax. **The same gap
existed in `horrorchatmessages`** (its hauntedcore dependency is `optional`
there, not `required`) — fixed there too, in a follow-up commit to that
already-pushed repo.

## API port — file by file
Only 3 files had Forge API surface:

| File | Change |
|---|---|
| `PhantomJoinMod.java` | Same pattern as the other mods: no-arg `@Mod` constructor → `(IEventBus, ModContainer)`; kept `Type.CLIENT`, confirmed against the real 1.21.1 sibling |
| `PhantomJoinConfig.java` | `ForgeConfigSpec(...)` → `ModConfigSpec(...)` |
| `client/PhantomJoinClientEvents.java` | `TickEvent.ClientTickEvent`+`Phase.END` → `client.event.ClientTickEvent.Post` (client-side path, same as hauntedcore's — **not** the server-side `event.tick.LevelTickEvent.Post` path used in `horroractionbar`/`misplacedambience`); `ClientPlayerNetworkEvent.LoggingIn`/`RegisterClientCommandsEvent` repackaged; nested `Mod.EventBusSubscriber(bus=FORGE)` → top-level `@EventBusSubscriber` with no bus param — this also covers the `onPresenceEnd(PresenceEndEvent)` handler, since hauntedcore's own event (already ported to extend `net.neoforged.bus.api.Event`) fires on the same general game bus as the other three handlers in this class |

No judgment calls beyond the already-established `.Post`/phase-check pattern
(same reasoning as documented for the other mods — convergent evidence
across siblings, and this file specifically matches hauntedcore's own
client-tick-event translation exactly since both are client-side).
